# 下层车：双板控制、通信与供电迭代

截至 2026-10-16，采用四个 MG370 编码器电机、胶轮、两块 TB6612、STM32F103C8 和 ESP32-S3-N16R8。四轮 PI、ESP32 BLE 和 Android 静态网页面板已实现源码，本轮未烧录、实板测试或发布。建模、底盘、机械机构和料仓由团队确认已完成，最新模型待上传；不能从旧 CAD 推定当前尺寸、舵机数量或运动范围。

## 四轮驱动与双板职责分配

**2026-10-03 旧方案：**仓库曾记录双 STM32F103 的 MG370 分工。后来决定由 ESP32 对接未来手机输入、STM32 处理底层控制，因此不沿用旧双 F103 协议或 USB 诊断作为现行控制方案。

**2026-10-13 实现：**新增独立 `board-link` 构建目标，共用 C 协议和状态机。STM32 只链接通信、延时与必要芯片支持，不链接上层 TT/PS2 电机后端，从构建层面隔开两车引脚和行为。

该次 `board-link` 固件只完成 TB6612、四轮编码器和舵机的资源预留，固定禁止电机，PB15/STBY 与 PB6–PB9/PWM 保持低。编码器帧有四路计数、有效位和年龄，但该目标没有采样，`valid_mask=0`；不能把零计数当作实测静止。

**2026-10-16 开环阶段：**下层改用胶轮，上层保留原麦轮；两车不再用同一底盘结论。新增独立 `lower-motor` 目标，实现 TIM4 四路 20kHz PWM、±250‰ 台架上限、1000‰/s 斜坡与反转过零等待 50ms。零目标、停止及命令失效时撤去驱动并滑行，不保证车体瞬时停止。1kHz 时基监控主循环，失活 50ms 后锁存关闭 STBY，IWDG 作为后备。

该阶段增加 TIM2/3/1 的三路 4 倍编码器采样和 PB10/PB11 的一路 2 倍采样，回传原始 32 位计数，当时还没有轮速闭环。ESP32 同时新增 USB `PWM`、`STOP`、`ENC` 命令；PWM 使用独立消息和能力检查，不把 mm/s 请求当作占空比，旧输入不自动续期。详情见 [电机与编码器说明](06-lower-motor.md)。

**2026-10-16 闭环与遥控阶段：**同一 `lower-motor` 目标接入四轮整数 PI，每 10ms 按实际时间差计算轮速，使用速度斜坡、反转过零等待 50ms、25% PWM 上限，以及编码器/方向/控制周期异常和驱动期间 500ms 无计数进展锁存。用户图片给出 13PPR、3.3–5V 供电及输出上拉到 VCC，编码器 VCC 因而采用 STM32 3V3；六针线序与方向待实测。按 13PPR 为电机轴单相周期、34:1 和 65mm 轮径假设，CPR 初值为 1768/1768/1768/884，四轮均默认未确认。PI 初值 Kp=1、Ki=2，加速度 500mm/s²，不作为已调好的参数。

ESP32 已增加单客户端 BLE GATT 与 Android 静态面板，支持方向、0–300mm/s 限速、停止、灯控和逐轮参数设置。回调只排队，原接收时刻用于命令有效期；停止、断连、溢出、过期会锁定并换会话，重连不续跑。STM32 参数只在 RAM，重启四轮均未确认；网页 localStorage 不会自动发送保存的参数或解锁。协议与操作见 [速度闭环与手机遥控](08-speed-remote.md)。本轮新固件与网页未烧录、未实板动作、未发布；构建与主机测试见 [验证记录](04-validation.md)，UBSan 未运行，历史灯控证据不能替代新功能验收。

中期后采用 [四目标导航＋人工末端调整](07-semi-auto-plan.md)：STM32 负责底盘闭环、连续里程计和动作执行，ESP32 负责路网、目标和任务状态。该导航部分仍是方案，未实现。

## 双板 UART 与超时恢复

**2026-10-13：**实现 115200、8N1、3.3V UART。使用 COBS 分帧、CRC16、版本/长度检查、严格序号和会话令牌，把噪声、错包、重发和旧连接积压包分开处理。

控制输入最长有效期 200ms；有效控制到期先处理撤销，再解析新输入。普通状态/握手帧不能给旧控制续期。300ms 没有有效同伴消息则断联，重新握手后才接受新会话命令。输入源序号和剩余有效期单独检查，避免未来 BLE 断开后不断重发缓存输入。

一开始有串口脚方向混淆。排障时把两个候选脚先设为输入观察：GPIO6 收到 CRC 正确、序号递增的 STM32 STATUS，GPIO4 没有，随后调整 ESP32 软件方向。当前接线为 **GPIO4 TX→PA3 RX，GPIO6 RX←PA2 TX，GND 共地**。这比单凭发送计数判定链路成功更可靠，调整后未重烧 STM32。

在 ESP32 中加入 `INFO`、有界接收字节追踪、错误计数和显式接收上拉，帮助区分“提交发送”“收到字节”“解析成功”三个状态。代码见 [共享协议](../firmware/shared/)、[ESP32 入口](../firmware/esp32/src/main.cpp)、[STM32 入口](../sample-mecanum-car-study/examples/board-link/main.c)。

## ESP32 控制 STM32 板载灯

**2026-10-13：**增加 `LED_SET` 和 `LED_ACK`，经 ESP32 USB 文本命令控制 STM32 PC13。一次只允许一个请求，500ms 内未完成则失败；ACK 需同时匹配请求序号、目标状态和会话，不能挤占控制/状态心跳或延长电机控制有效期。换会话或失联时清除灯请求并关灯。

两端已写入并独立读回一致。三轮 ON/OFF 共六次 ACK，队员随后目视确认约半秒亮灭；ACK 仅证明指令处理，目视观察作为单独证据。ESP32 复位后重新握手也通过。原始小体积记录见 [首次三轮测试](evidence/board-link-led-20261013.json)、[复测](evidence/board-link-led-repeat-20261013.json)、[复位后运行](evidence/board-link-post-reset-20261013.json)。

**2026-10-16 上传前历史基线复验：**两套主机测试与两端 `board-link` 构建通过；STM32 5376 字节、ESP32 289760 字节，重建 SHA256 与此前写入并读回版本一致。该结论属于新增电机后端之前的基线，不代表当前源码产物；没有在该上传任务中再次烧录或控制硬件。UBSan 因缺库未运行。

## 12V 动力与 5V 控制供电

**2026-10-13 排障：**移除 ST-Link 后 STM32 没有独立电源，两灯变暗；移串口脚导致亮度变化不能证明供电正常。读取记录为断联，不能用 UART 保护路径反向供电维持正式运行。保留该失败记录用于说明供电是通信前提，见 [断电后的链路状态](evidence/board-link-unpowered-stm32-20261013.json)。

**2026-10-15 整理方案：**四节 18650 为 2S2P，官方无线继电器受控输出之后并联两路：升压 12V 给两块 TB6612 VM，降压 5V 给两个开发板的 5V 输入；STM32 3V3 给两块 TB 的逻辑 VCC，所有 GND 共地，两主控 3V3 输出不互并。舵机只预留，具体供电等型号确认后再设计。

选择两路并联输入，是为了控制电源不依赖 12V 动力升压支路。普通满充 4.2V 电芯时，电池满电 8.4V。商家公式在 8.4V→12V 给出的 MAX 约 4.41A，仅是其标称算法，不能写成四电机实际连续输出验收。整车负载、温升和电压跌落仍待测。

**2026-10-16 核对：**5V 降压支路已装配，12V 升压支路未完成；当前面包板，中期后改洞洞板。新编码器资料确认允许 3.3V 供电且输出上拉至 VCC，四个编码器统一由 STM32 3V3 供电，先核对物理线序和板载稳压余量。机械完成与电源装配、驱动后端、实际行驶验收分别记录。逐线表和电机/编码器分配见 [接线说明](lower-car-wiring.md)。

## 开源使用说明

STM32 使用已有开源学习工程的启动、延时及 CMSIS/ST 标准外设库，ESP32 使用 Arduino-ESP32 2.0.17 和 PlatformIO Espressif32 7.1.3。共享协议、连接状态机及测试源码在本仓库公开；旧双 F103 PR 未合并、未复用为当前通信实现。完整来源和修改边界见 [第三方清单](05-open-source.md)。
