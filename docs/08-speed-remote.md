# 下层车轮速闭环与 Android BLE 遥控

更新：2026-10-17。STM32 四轮 PI 速度环、ESP32 BLE 服务和 Android 网页面板源码已完成。`lower-motor` 已修复看门狗启动问题并烧录，通信、灯控、故障诊断验证见 [修复记录](11-lower-watchdog-fix.md)；**逐轮及四轮 20%/25%、各 5s 架空开环试转通过；电脑 BLE 在 USB 供电下完成临时参数直行短测并停车，但独立供电后无广播；精确标定、闭环调参、手机实连和网页发布仍未验收**。ESP32 保留测试前的 `crtc-lower-pid-v2 source=BLE`，未在本轮重刷。

## 编码器参数与校准入口

**2026-10-16 用户提供：**MG370 霍尔编码器、减速比 34:1、13 PPR、供电 3.3–5V，商品图轮胎直径 65mm。追加参数图说明输出自带上拉，默认上拉至编码器 VCC，因此当前采用 **STM32 3V3→四个编码器 VCC**，共地；六针物理线序不能按颜色猜测。电机动力两线仍接 TB6612 输出。

商家图没有定义 13 PPR 是否已经包含倍频。先按“电机轴每转单相 13 个完整周期”计算初值：

| 轮位 | 采样方式 | 每轮一圈初始计数 |
|---|---|---:|
| M1 右前 | TIM2，4 倍 | 13×34×4 = 1768 |
| M2 左前 | TIM3，4 倍 | 1768 |
| M3 右后 | TIM1，4 倍 | 1768 |
| M4 左后 | A 相双沿 EXTI，2 倍 | 13×34×2 = 884 |

以上是待验证换算，不是标定结果。驱动锁定时，给轮胎做标记，记录面板原始计数，沿车辆前进方向手转一圈或数圈，计算 `abs(末计数−初计数)/圈数`，逐轮填写 CPR。正向手转若计数减少，编码器方向设为负；电机方向用已具备的 USB 单轮低占空比台架工具确认，见 [电机说明](06-lower-motor.md)。轮径可用实际滚动距离除以圈数和 π 校准。

2026-10-17 手转方向核对：前进统一定义为**轮胎最上方胎面朝实际车头移动**，不能把左右轮从外侧观察的顺时针当作同一物理前进方向。用户当前轮位称呼对应的结果如下；通道指原始编码器数组下标加一，不代表已经核对的电机输出通道。

| 当前轮位称呼 | 原始编码器通道 | 前进计数符号 | 明确方向后的计数变化 |
|---|---:|---|---:|
| 左后 | 4 | 正 | 1 圈 +922 |
| 右后 | 3 | 负 | 1 圈 -1820 |
| 左前 | 2 | 正 | 3 圈 +5374 |
| 右前 | 1 | 负 | 1 圈 -1741 |

随后四路分别完成 +15%、2 秒电动试转及用户目视确认：M1 右前、M3 右后向前；M2 左前、M4 左后向后，均停下。电机和编码器按同编号配对，无需重排编码器。按 M1–M4 顺序，电机方向系数为 `[+1,-1,+1,-1]`，编码器方向系数为 `[-1,+1,-1,+1]`。M4 首次窗口仅变化 -23 且用户未观察，复测持续变化约 -1051 并确认转动；首次异常原因未定。

以上方向核对已完成，CPR 和轮径仍是粗测/标称值，未写入校准确认或验收闭环。源码已按实测修正左右轮目标与遥测分组，网页标签和默认方向同步更新，并更换本地配置缓存键，避免旧轮位配置被自动载入；`confirmed` 仍全部为 false。源码修正尚未烧录实板，不能沿用旧左右混控进行转向验收。校准中曾静止掉线；接紧电池盒后有稳定窗口，尚不代表长期稳定性通过。[原始证据](evidence/manual-encoder-calibration-20261017.json)。

网页逐轮提供 CPR、轮径、电机方向、编码器方向、Kp、Ki、最大轮速及“实测确认”。四轮默认都未确认，不能解锁闭环；确认必须建立在实际测量上。配置只保存在 STM32 RAM，STM32 重启后重新写入；浏览器可保存表单，但重新打开会清除确认勾选，不自动下发或解锁。

## 四轮 PI 速度闭环

**2026-10-17 电脑 BLE 直行短测：**以已核对的方向、粗测 CPR `[1756,1791,1774,898]` 及标称 65mm 轮径作为临时台架配置，逐包收到配置 ACK 后解锁，仅发送四轮同目标的 80mm/s 直行，命令窗口约 2 秒。第一次因 Windows BLE 写回执耗时叠加额外延时，150ms 指令过期触发锁定；调整为将写入耗时计入周期并使用固件允许的 200ms TTL 后，第二次 16 条速度命令完成，后段四轮反馈约 68–70mm/s，未报运动故障。STOP 后确认目标/实测速均零，并通过配置 ACK 撤销四轮临时确认（ready_mask=0）；参数数值留在 RAM，重启或重新配置才替换。用户随后确认看到转动，未逐轮确认全部转向。

本次控制链路为电脑 BLE→ESP32→UART→STM32，ESP32 仍由 USB 供电，未通过 USB 下发电机命令、未刷固件；只测直行，不能据此认定旧左右分配已修正。用户随后表示看到转动，但未逐轮确认全部转向。拔掉 USB 后用户确认外部供电接回、电源灯亮，重复扫描及按 ESP32 RESET 后仍未发现广播，因此独立供电运动重测未开始；待测板上电压，根因未定。粗测参数不等同精确标定，短测不等同 PI 跟踪精度、落地行驶或手机验收。[完整证据](evidence/ble-straight-bench-20261017.json)。

**2026-10-16 实现：**独立 `lower-motor` 目标保留开环台架模式，另由 `CONTROL` 消息承载 mm/s 目标。每约 10ms 按实际采样间隔计算轮速，停车和手动转轮期间也持续更新；原始编码器累计计数不因停止清零。

默认 Kp_milli=1000、Ki_milli=2000，分别对应 Kp=1‰/(mm/s)、Ki=2‰/((mm/s)·s)。默认目标斜坡 500mm/s²、每轮最大目标 300mm/s、PWM 限幅 ±250‰。这些是保守调试初值，不保证实际 MG370 已能起转或稳定跟踪。PI 采用条件积分抗饱和，反向先过零再滑行等待 50ms，不叠加第二套开环斜坡。模式切换另从真实撤去驱动时刻计算至少 50ms，不能通过 STOP、换会话或切换 PWM/速度模式跳过。

任一轮配置未确认、编码器样本失效/异常跳变、持续反向反馈、连续驱动 500ms 无计数进展或循环超时，都会禁止输出并锁存相应故障。停止后继续测速，清故障要求无使能命令、输出已关闭、反馈有效且测得速度不超过 5mm/s，并保持至少 50ms 驱动关闭；清除不自动恢复旧动作。此无进展判断不替代电流检测，噪声计数也可能掩盖机械卡滞。

速度上限由 ESP32 按已获 STM32 ACK 的四轮配置最小值进一步限制，左右目标等比缩放以保留转向比例。零目标、显式 STOP、输入失效或故障撤去驱动并滑行，停车距离仍要实测。当前没有里程计、自动直行/转角动作、四目标路线执行或舵机动作。

## ESP32 BLE 与手机操作

2026-10-17 独立供电对照：原外部 5V 支路下，ESP32 红灯亮但广播消失，复位未恢复；用户没有万用表。改接充电宝/USB 充电器后广播恢复（具体电源型号未说明），在不连接电脑 USB 的条件下再次完成临时参数 80mm/s、约 2 秒 BLE 直行短测，四路速度反馈有效、无运动故障，最终目标/实测速全零且恢复锁定、撤销确认。用户确认四轮都向前转动并停下。这排除了“必须有电脑 USB 数据连接才能运行”的解释，但原外部电源路径/供电切换问题尚未定位，不能推定降压模块损坏或电池供电验收通过。

看门狗故障使用故障码 **6**。此时底盘保持通信、灯控和遥测，但关闭电机输出，网页不允许 ARM。停车后显式清故障可清运行期锁存；IWDG 初始化失败不能被 CLEAR 绕过，必须修复并重启。STOP、重连和普通心跳均不会自动清除看门狗故障。

**2026-10-16 实现：**设备名 `CRTC-Lower-Car`，使用 ESP32-S3 的 BLE GATT，不使用经典蓝牙 SPP。服务、控制、状态 UUID 分别为 `2c4b0001`、`2c4b0002`、`2c4b0003` 加后缀 `-6f1a-4c9e-9b72-3c06f42b7d11`。控制带写响应，状态 read/notify，包长固定 20 字节。只接受一个连接；会话号用于拒绝旧输入，不是 PIN 配对或身份认证。

回调仅向有界队列写入原始接收时间和连接代际，owner loop 执行校验、调度及 UART 发送。STOP、断连、溢出优先处理。速度命令最长 200ms 有效，ESP32 只转发剩余时间；STM32 再扣除接收缓冲停留时间，LED、配置和心跳不延长运动命令。

[网页操作说明](../firmware/web/README.md) 与 [页面入口](../firmware/web/index.html) 位于 `firmware/web/`。Android Chrome 需在 HTTPS 页面使用 Web Bluetooth；电脑 `localhost` 可本地预览，手机访问电脑普通局域网 HTTP 不满足该条件。该限制依据 [Chrome 官方文档](https://developer.chrome.com/docs/capabilities/bluetooth)。当前仓库代码上传不代表网页已部署到 HTTPS 站点。

操作顺序：连接→停车校准并等四轮配置 ACK→手动 ARM→按住方向行驶。默认面板上限 100mm/s；四胶轮只提供前进、后退、左转、右转。松手发零速度并保留解锁；大 STOP 锁定并使旧会话失效。失联、页面隐藏/失焦、触控取消或调度中断后均清除动作，回来不能自动续跑。收到新会话只在页面本地锁定，不回发无限 STOP。

## 电脑 BLE 实板检查（2026-10-17）

Windows 通过 BLE 连接 `CRTC-Lower-Car`，收到主状态、编码器和轮速通知。最终一次检查中，STOP 确认锁定，灯亮/灭命令收到 ESP32 的源序号确认（未取得实物灯光确认）；中性 ARM 被固件拒绝，回报 `reason=7`、`ready=false`、校准就绪 `0/4`。随后 10s 主状态保持同一会话、UART 在线、无故障且未解锁。没有发送 DRIVE、修改校准或绕过门禁，蓝牙运动尚未验收。

早先独立供电时曾成功连接，但重连发生 GATT 服务发现超时，广播一度消失；用户切换为 USB 供电后恢复。最终控制命令仍走 BLE，USB 用于 ESP32 供电和先前诊断，不能据此认定独立供电/长期重连已稳定。STOP 会引起 UART 与 BLE 会话更新，诊断脚本须等握手稳定再发下一条命令。详细过程及失败记录见 [电脑 BLE 证据](evidence/ble-pc-connection-20261017.json)。

## 构建、测试与实板验收

构建仍使用 STM32 `--target lower-motor` 和 ESP32 PlatformIO 环境 `board-link`。STM32 的 `--target board-link` 是独立禁用输出基线，不能作为闭环固件。命令见 [项目记忆](../PROJECT.md)。

新增主机测试入口：`firmware/tests/run_speed_tests.py`、`run_remote_tests.py`、`run_bridge_tests.py`、`test_web_remote.mjs`。分别验证真实 PI 核心的量化电机仿真、BLE 包与有效期、BLE→UART 两端往返/ACK/故障，以及网页写队列、会话、ARM、STOP 与配置流程。缺 UBSan 的本机使用 `SANITIZE=0`；仿真不能代替真实参数校准。

实板顺序：正常独立供电及 STBY 外部下拉→手转逐轮确认计数→架空单轮确认电机方向→写入四轮校准→低速闭环调参→验证停止、断联、复位和故障锁定→再做地面直行与转向重复性测量。12V 支路、电流余量和实际机械停车效果仍须单独验收。
